## Purpose, source integrity and actor boundaries

This ticket adds **observability and human review only** to the
SC-001–SC-008/BN-001–BN-006 project. NO new expense, obligation,
cash receipt, bank transfer, noncash setoff, invoice completion or
snapshot modification is generated by a notification, reminder,
audit/report export or dispute event.

An invoice always retains its ORIGINAL source obligation IDs and date.
Real confirmed cash and confirmed NONCASH are separate columns;
pending cash only reserves availability. Snapshot at LOCK differs
from LIVE BN-005 balance by design.

### In-app notifications

Migration `022_settlement_cycle_notifications_disputes.sql`
extends the existing `notifications` table *compatibly*:
- Legacy settlement notifications remain attached to their
  original settlement with the same deduplication unique key.
- New cycle notices use a composite group+cycle FK, event-specific
  recipient+event_key unique index and **nullable system actor**.
  The existing inbox shows a system event as **Hệ thống**.
- AFTER INSERT triggers on existing immutable documents enqueue
  in-app notices for cycle review/lock, pair proposals, actor-specific
  decision events, committed NONCASH application, next-period
  original late invoice assignment, open/respond/close disputes.
- Notifications are emitted in the SAME transaction as the original
  event, so rolled-back writes produce no ghost alerts. Source event
  IDs serve as the idempotency key; a repeat never generates duplicates.
- Only current ACTIVE members may receive new notices; actor never
  receives their own action notice. Pair proposal/approval events
  target only the two actual participants, not a manager surrogate.
- Notifications reuse the existing push opt-in/preference,
  subscription and durable delivery queue; push failures never
  change financial state. No new external messaging provider.

### Daily reminders (not released)

Existing authenticated daily Cron reuses the installed
`/api/internal/push-drain` Bearer-protected scheduled worker.
`lib/settlement-cycles/reminders.ts` produces at most 40 reminders
per invocation, once **per subject + recipient + calendar day**:
- OWNER: review period ready for lock for over 24 hours;
- actual pair member missing approval on a live immutable proposal
  older than 12 hours but still within the 72-hour validity;
- actual **other** counterpart with a pending CASH request older
  than 24 hours;
- actual two-person participant whose dispute is awaiting response;
- OWNER: original late invoice unrecorded by a LOCKED snapshot.

No repeated "pay now" demand for expired/revoked/invalidated
proposals; a pending request is never described as confirmed.
The daily Cron attempts durable push delivery after inserting
reminders. Dedup uses PostgreSQL conflict protection, safe with
retries or concurrent workers.

**The reminder worker returns DISABLED outside** either a distinct
future authorized financial release or ALL three exact CI-only
conditions: `CI=true`,
`SC009_TEST_ONLY=isolated-pg17`,
`DATABASE_URL=postgresql://test:test@localhost:5432/group_expense`.
No enabled production reminder spam during the current NO-GO period.

### Two-counterparty disputes (no money rewrite)

A dispute is tied to an ORIGINAL `obligation_id` that belongs
to a specific group and a **LOCKED** cycle snapshot.

- Only the true debtor or creditor may open; actor ID is always the
  signed session. The other party is derived from the original
  obligation, not a client-supplied user. Owner, manager and admin
  have **no** ability to impersonate either person.
- One active thread per original obligation, with immutable
  `group_settlement_cycle_disputes` opening document.
- The counterpart may `respond`; only the original reporter can
  then `resolve`, or `withdraw` while open/awaiting. Both
  identities and order are independently checked in PostgreSQL,
  even on direct SQL writes. Terminal threads cannot be reopened,
  rewritten or deleted. If a new dispute exists after a prior
  closure, it is a **new** separately keyed audit document.
- All `group_settlement_cycle_dispute_events` are append-only.
  Exact idempotency keys return the same event; reused keys with
  different body/actor/action return 409; group row and source
  rows are locked consistently to serialize concurrent writes.
- Only the two counterparties may read the dispute content.
  A third group member (even admin/owner) sees no text or
  individual dispute audit event; the group reconciliation
  report may show only a **count** of still-open cases.
- Open/awaiting disputes block new cycle noncash applications,
  cycle batch CASH requests against the affected original
  outstanding and CONFIRMATION of an existing pending
  settlement allocating to that original obligation. They
  do not automatically cancel a pending settlement or reverse
  money already confirmed before the dispute. The original
  counterparties must resolve their own cash/ledger issue
  through existing procedures after review.
- Existing SC-005 cash submission maps a disputed-source
  PostgreSQL exception into a controlled HTTP 409, never a 500.
  BN-004/BN-006 retain their existing SQL error-to-409 path.

```
GET /api/groups/:groupId/settlement-cycle/cycles/:cycleId/disputes
POST /api/groups/:groupId/settlement-cycle/cycles/:cycleId/disputes
  { obligationId, reason (10–500 chars), requestKey (UUID) }

POST /api/groups/:groupId/settlement-cycle/cycles/:cycleId/disputes/:disputeId/events
  { eventType: "respond"|"resolve"|"withdraw",
    body (5–500 chars), requestKey (UUID) }
```

### Reconciliation and audit exports

```
GET /api/groups/:groupId/settlement-cycle/cycles/:cycleId/reconciliation
GET /api/groups/:groupId/settlement-cycle/cycles/:cycleId/audit?page=N
GET /api/groups/:groupId/settlement-cycle/cycles/:cycleId/export?kind=ledger
GET /api/groups/:groupId/settlement-cycle/cycles/:cycleId/export?kind=audit
```

Every endpoint requires a signed session and current ACTIVE group
membership, runs a **REPEATABLE READ READ ONLY** PostgreSQL
transaction against exactly one existing group+cycle identity.
Any non-member or archived group is denied.

- Report aggregates the **entire** SC-004 original snapshot through
  canonical live BN-005 SQL: `original - confirmedCash -
  confirmedSetoff = outstanding`;
  `outstanding - pendingCash = available`. Mismatched or
  negative values fail 409 rather than appearing as paid.
- Readiness is a read-only "ready for manual review" hint:
  zero outstanding, no unresolved pair dispute, no pending
  cycle cash, no uncompleted original invoice and no unresolved
  live proposal. It NEVER automatically closes the cycle.
  Rejected, revoked, expired or invalidated immutable
  proposals remain in history, but are NOT counted as unresolved.
- Audit reads chronological original source events: cycle,
  BN-002 proposal, BN-003 decision, BN-004 noncash,
  SC-005/BN-006 original CASH events, SC-006 late invoice,
  and SC-009 dispute/event. Pair-specific financial decisions,
  cash events and dispute texts are restricted to the
  two counterparties; never leak these records to a third
  group member via JSON audit or CSV.
- Financial source CSV includes each original obligation, invoice,
  original date, debtor, creditor and exact money columns,
  keeping all source records regardless of the page being
  displayed in the SC-008 UI. Audit CSV exports original
  record IDs, actor, event type and time.
- Exports have secure Content-Disposition and no-store headers,
  UTF-8 BOM for Excel and RFC4180-escaped quoted cells.
  Spreadsheet formula injection is neutralized by prefixing a
  single apostrophe for user text beginning with
  `=`, `+`, `-` or `@` after whitespace.
- A single export refuses rather than truncates when the
  original set or event count exceeds **20,000**. JSON audit
  uses 50-event pages; a limited group UI is NEVER used as
  a source for financial sums.
